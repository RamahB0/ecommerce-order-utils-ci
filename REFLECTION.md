# Reflection Report

The trickiest part was less any single tool and more the ordering between them: it is tempting to write code first and bolt on tests and CI afterward, but that produces a workflow branch full of commits that were never actually checked against a green build. Writing the CI workflow early, before most of the feature commits, forced every push on the branch to be verifiable rather than "probably fine." The ruff configuration also took a moment to get right, since its default rule set is narrower than tools like flake8 with plugins, so a first pass reported "all clear" on code that still had an unsorted, unused import block once I deliberately reintroduced one to confirm the linter was actually doing something.

The CI pipeline's main value was turning "did I break anything" from a manual, easy-to-skip step into an automatic gate on every push and pull request. Because linting and testing both run before a merge is safe, a regression shows up as a failed check on the PR itself rather than as a bug discovered later on main. The pipeline also surfaced one thing I hadn't planned for: a GitHub Actions runtime deprecation warning unrelated to the code, which is exactly the kind of drift a CI run catches automatically that a local test run never would.

Working on a feature branch with a pull request, rather than committing straight to main, gave the code review a concrete artifact to attach comments to and made three design decisions (input validation, where tax and shipping logic belongs, and turning a rebuilt dictionary into a module constant) explicit and recorded, instead of silently baked into the first draft. Combined with the QA report, the result is a change that is easy for someone else to trust without re-reading every line: the tests, lint status, and review rationale are all visible alongside the diff and the merge commit.
